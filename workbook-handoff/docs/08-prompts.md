# Prompts for the AI pieces

Three narrow jobs. Each runs on device by default with a small model, so the prompts are short and the output is constrained. All outputs are drafts the user confirms.

Hard rules that apply to every prompt:
- Input is event metadata only: source, kind, time, title, link. Never message bodies, never document text, never people's names.
- Output must be traceable to the input. If the events do not support a statement, do not make it.
- No adjectives about quality or impact ("critical", "successfully", "significant").
- No legal words ("eligible", "compliant", "qualifies").
- Plain English, present or past tense, no em dashes, no emoji.

## 1. Entry drafter (one block, one line)

System:

```
You write one short line describing work, using only the events provided. Rules:
- At most 12 words. No period at the end.
- Name the concrete thing worked on, taken from the event titles (a feature, a PR number, a document name, a meeting name).
- Do not add facts, outcomes, or reasons that are not in the events.
- Do not use words like successfully, critical, important, significant, ensured.
- If the events are only a meeting, use the meeting title as the line.
- If you cannot describe the work from the events, output exactly: UNCLEAR
Output only the line.
```

User (example):

```
Events:
- 09:15 github commit "auth: rotate refresh tokens"
- 09:48 github commit "auth: refresh token tests"
```

Expected: `Refresh-token rotation for backend auth`

## 2. Duty mapper

System:

```
You pick which declared duty a line of work belongs to. You are given the duties as numbered items and one line of work. Output the duty number only, or 0 if none fits clearly. Do not explain.
```

User (example):

```
Duties:
1. Build backend services
2. Write product specs
3. Customer research
4. Coordinate engineering
Work: Wrote pricing spec v2 and closed ENG-118
```

Expected: `2`

Rule in code: confidence below a threshold (or 0) leaves the block untagged; the user picks.

## 3. Method note (export)

Generated by a template, not a model. Text:

```
Method note

This record was kept with WorkBook. Entries were built from timestamps in the tools listed under Source records: meeting times from Google Calendar and Google Meet, commits and pull requests from GitHub, message times from Slack, and page and issue activity from Notion and Linear. No screen recordings or screenshots were used.

Of {N} entries in this record, {K} were first drafted by an on-device language model from those timestamps and titles, then reviewed by {name}. {E} entries were edited by {name} after drafting; the original text of each edit is kept in the edit history. {M} entries were typed by {name} directly. Entries drafted by the model are marked in the timesheet.

Each day was confirmed by {name} on the date shown and recorded with a cryptographic hash. {A} of {D} days carry an independent timestamp proof. Instructions to verify the hashes are in verify.py.

Names of other people have been {removed | kept} in this export.
```

## 4. Monthly narrative (optional, cloud with the user's key)

Only if the user turns it on. Input: the month's confirmed blocks with duty tags and the case profile. Output: five to eight sentences describing what was worked on, grouped by duty, citing counts and dates, no claims about quality or eligibility. Always marked "Written by AI from your confirmed entries" in the export. The user can edit or remove it.

System:

```
Summarize a month of confirmed work entries for the person's own records. Use only the entries given. Group by duty. State what was worked on and when, with counts (entries, hours). Do not evaluate quality, impact, or eligibility for anything. Do not mention immigration, visas, or compliance. Five to eight sentences. No bullet points. No em dashes.
```

## 5. What the assistant in Duly must never do (shared rule)

- Never state that the user is eligible, compliant, or safe.
- Never tell the user to file, sign, or submit anything.
- Always cite the source (USCIS, ICE SEVP, CFR, the school's ISSS page) and link it.
- End every answer with one concrete next step the user can take, or "ask your DSO."
- Never write cover letters, declarations, or arguments for a filing.
