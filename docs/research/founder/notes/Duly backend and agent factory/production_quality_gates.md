# Production-Grade AI-Agent Code: Quality Gates, Environment Parity, and Stack for Duly's Backend (2024-2026)

## Key Question 1: Why local-pass/prod-fail happens, and the parity practices that kill it

### Takeaway
The documented root causes are the classic 12-factor "dev/prod parity" gaps (tools gap, backing-service substitutes like SQLite-for-Postgres, config divergence) amplified by AI-specific failure modes: agents ship code the author cannot explain, and mocked dependencies plus high-line-coverage-but-weak tests hide flow-level bugs. The consensus fix is containerized parity (Docker Compose / devcontainers), real dependencies in tests via Testcontainers, and 12-factor config.

### Cited Findings
- 12-factor identifies three gaps behind deploy failures: time gap, personnel gap, tools gap; it explicitly warns against "lightweight local substitutes" such as SQLite instead of PostgreSQL or in-memory cache instead of Memcached, because "incompatibilities inevitably emerge, causing code to fail in production after passing development tests." Core rule: "Keep development, staging, and production as similar as possible" — [12factor.net/dev-prod-parity](https://12factor.net/dev-prod-parity)
- 12-factor notes containerization (Docker) and modern package managers make full local parity cheap enough that there is no longer a good excuse for divergent backing services — [12factor.net/dev-prod-parity](https://12factor.net/dev-prod-parity)
- AI-specific parity gap: "A developer who prompted Cursor to build an authentication flow may have shipped working code they could not explain line by line" — static analysis cannot detect flow-level logic errors; human review assumes author comprehension, which vibe-coded PRs break, "creating gaps between what passes CI and what works in production" — [Autonoma: Quality Gate for Vibe Coding](https://getautonoma.com/blog/quality-gate-vibe-coding)
- AI-generated test suites reach high line coverage while failing to detect faults: "high code coverage does not necessarily imply strong fault detection capability"; documented weaknesses include boundary blindness and "training-anchored assertions" (99% of semantically-altered tests still pass) — [Augment Code: Mutation Testing for AI-Generated Code](https://www.augmentcode.com/guides/mutation-testing-ai-generated-code)
- Testcontainers' pitch is exactly the mocked-deps failure: run integration tests against real Postgres/Redis/Kafka in throwaway Docker containers instead of mocks or shared test DBs, so tests exercise the same engine as production — [Docker: Testcontainers, Testing with Real Dependencies](https://www.docker.com/blog/testcontainers-testing-with-real-dependencies/); practitioner accounts of replacing mock-heavy CI with Testcontainers: [DEV: Stop Mocking Everything in Integration Tests](https://dev.to/mindinu/stop-mocking-everything-in-integration-tests-why-testcontainers-changed-my-ci-strategy-2akl)
- Testcontainers has first-class Python support (works with pytest fixtures spinning real PostgreSQL per test session) — [Testcontainers Python guide](https://testcontainers.com/guides/getting-started-with-testcontainers-for-python/); and Node.js/Postgres support — [Testcontainers Postgres in Node.js](https://qaskills.sh/blog/testcontainers-postgres-node-guide)
- Timezone/date bugs are a distinct documented class of hidden production failures (server TZ vs user TZ, DST transitions, boundary dates), addressed by explicit TZ-aware test design and injecting/controlling the clock in tests — [NashTech: Date and Time Testing, Finding Hidden Time Zone Bugs](https://blog.nashtechglobal.com/date-and-time-testing-finding-hidden-time-zone-bugs/)
- Property-based testing (Hypothesis) is documented as effective specifically at surfacing edge cases (boundary values, weird encodings, date extremes) that example-based tests written by humans or LLMs miss; Anthropic's own red team used Hypothesis with Claude to find real bugs — [Anthropic: Finding bugs with Claude and property-based testing](https://red.anthropic.com/2026/property-based-testing/); background: [Increment: In praise of property-based testing](https://increment.com/testing/in-praise-of-property-based-testing/)

### Inferences
- For Duly, whose core value is deadline/date math across visa timelines, the two highest-leverage parity practices are: (1) never test against SQLite when prod is Postgres (12-factor backing-services rule), and (2) inject the clock everywhere date logic lives (a `Clock`/`now()` dependency, frozen in tests), plus Hypothesis property tests over date ranges and timezones — this directly targets the app's most damaging failure class (a wrong OPT/grace-period deadline).
- A single `docker-compose.yml` (api + worker + postgres + redis-or-none + minio) used identically by dev, CI, and e2e is the minimum-viable parity mechanism for a solo founder; devcontainers add editor parity for agent sandboxes at near-zero cost.
- Concrete parity checklist derived from cited causes: pinned base images and lockfiles; `.env.example` + 12-factor env config with startup validation (pydantic-settings/zod), so config divergence fails fast at boot, not at request time; run migrations in CI against a fresh Postgres before tests (catches missing/broken migrations); seed data generated by the same factories tests use, with realistic volumes; UTC-only storage with TZ conversion at the edge.

### Gaps
- No rigorous published statistics quantifying what fraction of AI-agent PR failures are attributable to each cause (env drift vs mocks vs time bugs); the causal taxonomy is assembled from practitioner posts, not measured studies.

## Key Question 2: Gate pipeline for agent PRs — ordering, tools, thresholds

### Takeaway
The practitioner consensus (2025-26) is a fail-fast layered pipeline: format/lint → strict types → security scan (parallel) → unit+property tests with diff-coverage floor → integration on real containers → contract/e2e → mutation testing on changed code as the test-quality gate. Typical published thresholds: 0 lint warnings, strict TS/mypy, ~70% coverage on changed lines, high-severity security findings block, mutation score gated on changed code rather than whole repo.

### Cited Findings
- Autonoma's published gate order for AI PRs: 1) lint/format (~1 min, ESLint/Prettier/Biome with `--max-warnings 0`), 2) type check (~2 min, TypeScript `--strict`, `any` blocked), 3) security (~3 min, Semgrep OWASP ruleset + Gitleaks + npm audit, high-severity blocks merge), 4) test coverage (~5 min, 70% line coverage on changed files, not whole repo), 5) agentic/e2e testing (~10 min) — [Autonoma: Quality Gate for Vibe Coding](https://getautonoma.com/blog/quality-gate-vibe-coding)
- Mutation testing tools by language: mutmut (Python), StrykerJS (JS/TS, incremental mode since v6.2), PIT (Java); Meta's production deployment reached 73% acceptance of generated tests using mutation feedback; Google's Mutagenesis processed 760k code changes / 17M mutants; StrykerJS incremental mode reused 3,731 of 3,965 prior results in one documented run (only 234 mutants executed), making per-PR mutation gates affordable — [Augment Code: Mutation Testing for AI-Generated Code](https://www.augmentcode.com/guides/mutation-testing-ai-generated-code)
- No universal mutation-score threshold exists; recommended practice is to gate changed code first, raise thresholds on critical paths (payment/auth), and compare against historical module baselines — [Augment Code](https://www.augmentcode.com/guides/mutation-testing-ai-generated-code); real projects publish Stryker `break` thresholds around 80 for gated modules (with ratcheting up from lower initial values) — [example ratchet issue](https://github.com/fderuiter/portfolio/issues/968); Stryker practical guide with threshold config — [QASkills: Mutation Testing With Stryker](https://qaskills.sh/blog/mutation-testing-stryker-guide-2026); mutation-testing overview — [CircleCI: What is mutation testing?](https://circleci.com/blog/what-is-mutation-testing/)
- Schemathesis generates property-based test cases directly from an OpenAPI spec and runs as a CI step, catching contract violations (undocumented status codes, schema mismatches, server errors on valid inputs) without hand-written contract tests — [Schemathesis tutorial](https://www.davidmello.com/software-testing/test-automation/automated-api-testing-with-schemathesis); CI integration guides: [QASkills Schemathesis guide](https://qaskills.sh/blog/api-contract-testing-schemathesis-guide) and [Apideck: OpenAPI Testing complete guide](https://www.apideck.com/blog/openapi-testing) (which positions contract testing + fuzzing + integration as complementary layers)
- Static gates alone are insufficient for AI code: "Linting cannot tell you whether your checkout flow correctly handles a cart with a deleted product" (12 words) — [Autonoma](https://getautonoma.com/blog/quality-gate-vibe-coding)
- Broader AI-code quality-gate implementation guides confirming the same layer stack (static → tests → security → runtime verification): [Augment: Autonomous Quality Gates](https://www.augmentcode.com/learn/autonomous-quality-gates-ai-powered-code-review), [SoftwareSeni: Building Quality Gates for AI-Generated Code](https://www.softwareseni.com/building-quality-gates-for-ai-generated-code-with-practical-implementation-strategies/), practitioner account: [DEV: How I Validate Quality When AI Agents Write My Code](https://dev.to/teppana88/how-i-validate-quality-when-ai-agents-write-my-code-481c)
- Hypothesis is the standard Python property-based library (actively maintained, 8k+ stars) — [GitHub: HypothesisWorks/hypothesis](https://github.com/hypothesisworks/hypothesis); build guide with CI usage — [OneUptime: How to Build Property-Based Testing with Hypothesis](https://oneuptime.com/blog/post/2026-01-30-how-to-build-property-based-testing-with-hypothesis/view)

### Inferences
- Recommended concrete pipeline for Duly (Python side): ruff format+lint (0 warnings) → mypy --strict → gitleaks + semgrep (OWASP + `p/python` rulesets; high severity blocks) + pip-audit → pytest unit + Hypothesis property tests on all date/deadline math → diff-coverage floor ~80% on changed lines (Autonoma's 70% is the published floor; date-math modules should ratchet higher) → integration tests on Testcontainers Postgres with migrations applied → schemathesis against the FastAPI-served OpenAPI spec → Playwright e2e against the compose stack → mutmut on changed files only (incremental), gate "no new surviving mutants in changed code" rather than a repo-wide percentage. TS side mirrors: biome/eslint, tsc --strict, fast-check for property tests, StrykerJS incremental with `break` ratcheted toward 80 on core modules.
- Ordering principle: cheapest-and-most-deterministic first; anything flaky or >10 min (mutation full runs, e2e suites) goes on merge-queue/nightly, not per-push — this matches Autonoma's timing budget and Stryker's incremental-mode design.
- Pact-style bidirectional contract testing is likely overkill for a solo founder with one API and one frontend; schemathesis-from-OpenAPI gives most of the value with zero consumer/provider ceremony.

### Gaps
- k6 performance-smoke budgets: I found no 2024-26 source publishing typical latency/error budgets used as PR gates for small SaaS; teams appear to run perf smoke on schedule, not per-PR. Recommend p95 budget gates only after real baselines exist — this is inference, not cited.
- No authoritative single source for a "standard" diff-coverage number; 70% (Autonoma, changed files) is the only concretely published figure found.

## Key Question 3: Prod-shaped local — same artifacts locally and in prod

### Takeaway
The pattern with the most support: one Dockerfile + one docker-compose stack that is the unit of truth; deploy the same image to a container PaaS (Railway/Render/Fly.io). Use real Postgres locally (never SQLite-for-dev when prod is Postgres, per 12-factor), and wire structured logs/OpenTelemetry from day one so local and prod emit identical telemetry.

### Cited Findings
- 12-factor: identical backing services across environments; resist SQLite-locally-Postgres-in-prod — [12factor.net/dev-prod-parity](https://12factor.net/dev-prod-parity)
- SQLite vs Postgres 2025 comparisons converge: SQLite is production-legitimate for single-node, read-heavy, embedded workloads, but Postgres is the verdict for multi-user SaaS needing concurrent writes, roles/permissions, RLS, and managed hosting — [Airbyte: SQLite vs PostgreSQL](https://airbyte.com/data-engineering-resources/sqlite-vs-postgresql), [DevOps Daily verdict](https://devops-daily.com/comparisons/sqlite-vs-postgresql), [kunalganglani.com 2026 comparison](https://www.kunalganglani.com/blog/sqlite-vs-postgresql-for-apps)
- PaaS vs K8s for small teams: "If you just want a small app and its database online without learning Kubernetes, all three work" (Railway, Render, Fly.io); "Railway is my default recommendation for someone who describes themselves as 'not a DevOps person'"; Railway and Render provide managed Postgres with automatic backups as first-class resources, Fly.io expects more self-management — [DEV: Railway vs Render vs Fly.io](https://dev.to/libme/railway-vs-render-vs-flyio-deploying-a-hobby-app-without-a-devops-team-10d3) (note: only one quote should be used per source in the final report; both captured here for the writer to choose)
- Pricing/benchmark comparison of the three PaaS with 2026 numbers (Railway usage-based, Render per-instance with blueprints/IaC-in-repo, Fly.io machine-based with scale-to-zero) — [Techsy benchmarks](https://techsy.io/en/blog/railway-vs-render-vs-fly-io), [DevOpsBoys comparison](https://devopsboys.com/blog/render-vs-railway-vs-fly-io-paas-2026)
- Dagger's pitch is precisely "same pipeline locally and in CI": pipelines-as-code executed in containers, eliminating "works in CI but not locally" divergence, with content-addressed caching — [DEV: Deep Dive into Dagger CI (Part 1)](https://dev.to/sami_chibani/cicd-in-the-era-of-ai-and-platform-engineering-a-deep-dive-into-dagger-ci-part-1-58pi); case study of PR-to-production speedup — [Dagger blog: Discern use case](https://dagger.io/blog/discern-use-case/)

### Inferences
- For Duly: one multi-stage Dockerfile per service (api, worker, llm-gateway), one compose file with profiles (`dev`, `test`, `e2e`); CI builds the image once and every downstream gate (integration, e2e, deploy) uses that exact image digest — "test the artifact you ship."
- LocalStack only if/when an AWS-only dependency appears (SES, S3 — though MinIO in compose covers S3-compatible object storage without LocalStack); avoid adopting AWS primitives early precisely to keep local parity trivial.
- Observability from day one at solo scale means: structured JSON logs (loguru/pino) with request IDs + tenant IDs, OpenTelemetry SDK auto-instrumentation for FastAPI/SQLAlchemy exported to a free-tier backend (Grafana Cloud/Honeycomb), and the same exporter config locally (console exporter) — inference from standard practice; no single citation found that argues this for solo founders specifically.
- Feature flags at this scale: a Postgres-backed flags table or env-var flags beat adopting LaunchDarkly-class tooling; no strong 2025 citation found either way (gap).

### Gaps
- No head-to-head 2025-26 source measuring deployment-failure rates of compose-parity teams vs non-parity teams (the parity benefit is argued, not measured).
- Feature-flag tooling for solo founders: no citable consensus source found.

## Key Question 4: Agent-specific CI — ephemeral envs, caching, auto-revert, branch protection

### Takeaway
The 2025-26 pattern for agent swarms: every PR/worktree gets an ephemeral containerized environment; caching (Dagger content-addressed cache, Depot remote builders, GHA cache) keeps swarm CI affordable; GitHub merge queues re-verify the combination of green PRs before they land, which is the documented mechanism for keeping main green at agent scale; branch protection requires all gates + human approval for agent-authored PRs.

### Cited Findings
- Ephemeral execution environments are now a named product category for AI agents (2026): isolated per-task sandboxes/microVMs that spin up per run and are destroyed after — [Northflank: Ephemeral execution environments for AI agents](https://northflank.com/blog/ephemeral-execution-environments-ai-agents)
- Dagger positions itself for the AI-agent era: containerized, portable pipelines with content-addressed caching so repeated agent runs only recompute what changed; case studies report large CI speedups (OpenMeter: 5x faster pipeline) — [OpenMeter/Kong: How We Made Our CI Pipeline 5x Faster](https://openmeter.io/blog/how-we-made-our-ci-pipeline-5x-faster), [DEV: Dagger CI Part 2](https://dev.to/sami_chibani/cicd-in-the-era-of-ai-and-platform-engineering-a-deep-dive-into-dagger-ci-part-2-3e75)
- GitHub merge queue exists precisely because two individually-green PRs can be jointly red: the queue creates temporary branches merging queued PRs with latest main and requires checks to pass on the combination before merging — [GitHub Docs: Managing a merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue); explainer of the green-PR-breaks-main failure mode — [DEV: GitHub Merge Queue, Explained](https://dev.to/pyor/github-merge-queue-explained-why-green-prs-break-main-2bk1); merge queues framed as the mechanism for "keeping CI green at agent scale" — [learncursor.dev: Merge Queues Explained](https://www.learncursor.dev/learn/cursor-origin/merge-queues); tool options beyond GitHub's (Mergify, Graphite) — [Graphite: merge queue tools](https://graphite.com/guides/merge-queue-tools-options)
- Practitioner guidance on agent PRs: revert-first when an agent PR you cannot explain breaks production; treat rollback as the default over debugging under pressure — [DEV: First Rollback, Revert the Agent PR You Cannot Explain](https://dev.to/gitgo_5662/first-rollback-revert-the-agent-pr-you-cannot-explain-3akh)
- Warning: my search for auto-revert-on-red-main norms surfaced mostly agent-generated GitHub repos with contradictory policies (auto-revert bots vs "fix forward, never revert" rulings), e.g. [a11ign PR #2389](https://github.com/a11ign/a11ign/pull/2389); these are low-quality sources and I do not treat them as consensus. The reliable primitives are merge queue (pre-merge) and cheap `git revert` + redeploy (post-merge).

### Inferences
- Solo-founder-sized agent CI: GitHub Actions with (a) path-filtered jobs so docs-only agent PRs don't run the full matrix, (b) `concurrency` groups cancelling superseded runs per branch, (c) GHA dependency+Docker layer caching or Depot builders if image builds dominate, (d) merge queue on main with the required-checks subset (lint, types, unit, integration) running per-queue-entry and heavy suites (mutation, e2e, perf) nightly. Dagger is worth adopting only if the founder wants agents to run the identical pipeline locally in their worktrees; otherwise plain GHA + compose is simpler.
- Branch protection for agent authors: require merge queue, require all status checks, require 1 human review (the founder) on anything touching auth/RLS/migrations/billing via CODEOWNERS, forbid direct pushes to main, and enable auto-delete of merged branches. Post-merge safety = deploy-on-green from main + one-command `git revert` + PaaS rollback to previous image.
- Cost control for swarms: run the expensive tier (mutation, e2e, agentic testing) only on `ready_for_review` non-draft PRs (Autonoma's documented scoping) and on the merge queue, not on every agent push.

### Gaps
- Depot-specific pricing/perf numbers for agent-swarm workloads: not found in this pass (only category-level claims).
- No published quantitative norms for "acceptable CI spend per agent PR."

## Key Question 5: Backend shape for Duly — reference architecture, right-sizing, K8s path

### Takeaway
Right-sized 2025-26 shape for a compliance SaaS at solo scale: one FastAPI (or single TS) service + managed Postgres with RLS for tenant isolation + a Postgres-native job queue (transactional enqueue in the same DB) + S3-compatible object storage + an LLM gateway layer with audit logging, all as containers on Railway/Render/Fly.io. Kubernetes now is documented overkill; Temporal is overkill until workflows span services or need durable long-running orchestration.

### Cited Findings
- Postgres RLS is the widely documented pattern for shared-schema multi-tenant SaaS isolation: policies keyed on `current_setting('app.tenant_id')` set per request/connection, enforcing isolation in the database rather than trusting every query's WHERE clause — [The Nile: Shipping multi-tenant SaaS using Postgres RLS](https://www.thenile.dev/blog/multi-tenant-rls), [DEV: PostgreSQL RLS for Multi-Tenant SaaS](https://dev.to/software_mvp-factory/postgresql-row-level-security-for-multi-tenant-saas-1lgp), deep-dives: [ricofritzsche.me RLS multi-tenancy](https://ricofritzsche.me/mastering-postgresql-row-level-security-rls-for-rock-solid-multi-tenancy/), [wellally.tech B2B RLS guide](https://www.wellally.tech/blog/postgres-multi-tenant-database-row-level-security); documented RLS gotchas include connection-pooling with session settings and table owners bypassing RLS unless `FORCE ROW LEVEL SECURITY`
- Postgres-as-queue verdict: with `FOR UPDATE SKIP LOCKED` a Postgres queue handles "job rates well beyond what most applications produce"; "Start with Postgres if your jobs are enqueued by the same application that owns the database"; migration triggers are dequeue latency showing up in DB wait events (→ Redis) or queues spanning services/teams (→ SQS); operationally, "autovacuum tuning on high-churn tables matters more than dequeue query optimization" — [DEV: Postgres as a Job Queue vs Redis vs SQS](https://dev.to/libme/postgres-as-a-job-queue-vs-redis-vs-sqs-when-does-just-use-your-database-stop-working-1f24) (writer: use at most one of these quotes)
- Named pg-native queue implementations: River (Go, from the author of the canonical pg-queue posts) — [brandur.org/river](https://brandur.org/river), [riverqueue.com](https://riverqueue.com/); Graphile Worker and pg-boss for Node — referenced in [the same DEV comparison](https://dev.to/libme/postgres-as-a-job-queue-vs-redis-vs-sqs-when-does-just-use-your-database-stop-working-1f24)
- Temporal vs Celery (2026 practitioner comparisons): Celery = simple distributed task queue (needs Redis/RabbitMQ broker), Temporal = durable workflow orchestration with replayable state, retries and long-running human-in-the-loop steps; Temporal recommended when workflows are multi-step, long-lived, and must survive worker crashes with exactly-once semantics; Celery/simple queues recommended for fire-and-forget background jobs — [dasroot.net: Orchestrating AI Tasks with Celery vs Temporal](https://dasroot.net/posts/2026/02/orchestrating-ai-tasks-celery-temporal/), [Markaicode: Temporal vs Celery](https://markaicode.com/vs/temporal-vs-celery/), [App Stack Builder comparison](https://appstackbuilder.com/compare/celery-vs-temporal)
- PaaS-over-K8s consensus for small teams (see KQ3 citations): Railway/Render/Fly.io all deploy Docker images with managed Postgres, no K8s knowledge required — [DEV: Railway vs Render vs Fly.io](https://dev.to/libme/railway-vs-render-vs-flyio-deploying-a-hobby-app-without-a-devops-team-10d3)
- OWASP Top 10 for LLM Applications 2025 (official) lists the risks an LLM gateway must gate: LLM01 Prompt Injection, LLM02 Sensitive Information Disclosure, LLM05 Improper Output Handling, LLM06 Excessive Agency, LLM10 Unbounded Consumption — mitigations include input/output filtering, least-privilege tool access, and rate/spend limits — [OWASP GenAI: Top 10 for LLM Applications 2025](https://genai.owasp.org/resource/owasp-top-10-for-llm-applications-2025/); explainers: [Aembit](https://aembit.io/blog/owasp-top-10-llm-risks-explained/), [Oligo Security](https://www.oligo.security/academy/owasp-top-10-llm-updated-2025-examples-and-mitigation-strategies)

### Inferences
- Duly-specific verdict: FastAPI monolith (single deployable) + worker process sharing the codebase; Postgres with RLS (tenant_id = user account) on Railway or Render managed Postgres; queue = a Postgres-backed library in the app's language (Python: Procrastinate or a SKIP LOCKED table + the worker; TS: Graphile Worker/pg-boss) because ingestion of policy updates and notification fan-out are exactly "jobs enqueued by the app that owns the DB." Temporal only if/when multi-week visa-workflow orchestration with human steps outgrows job semantics. Skip Redis entirely at launch (one less service to keep in parity).
- RLS caveats to encode as CI checks: an integration test that connects as the app role, sets `app.tenant_id`, and asserts cross-tenant reads return zero rows; plus a lint/migration check that every tenant-scoped table has an RLS policy (policy-coverage test). This is the single most compliance-relevant automated gate for Duly.
- LLM narration service: run it as a thin gateway module that (a) logs every prompt/response with tenant ID and model version to an append-only audit table (compliance need: users act on immigration guidance), (b) validates/schemas LLM output before it touches deadlines (LLM05), (c) enforces per-tenant token budgets (LLM10). Because narration is advisory, deterministic date math must live in tested Python/TS code, never in the LLM.
- K8s-later path: because everything ships as OCI images with env-var config behind a compose topology, migrating later means writing manifests/Helm for the same images — no application changes; this is the standard argued benefit of container-PaaS-first, though no single source states the migration path explicitly (inference).

### Gaps
- No 2025-26 source found giving a reference architecture specifically for a small *compliance* SaaS (immigration/legal); the shape above is assembled from multi-tenant SaaS + queue + LLM-security sources.
- Python-native pg-queue libraries (Procrastinate, SAQ) were not directly evaluated by the sources found; River is Go-only, so it is a pattern reference, not a direct dependency for a FastAPI stack.

## Key Question 6: Definition-of-done / production-readiness checklists (PRR-lite)

### Takeaway
Google's SRE PRR model and 2025 practitioner checklists converge on a short list a solo founder can enforce per feature: monitoring/alerts defined, runbook exists, backup/restore actually tested (not just configured), rate limits and idempotency on external-facing/retried operations, rollback path verified.

### Cited Findings
- Google SRE's Production Readiness Review is the origin pattern: a structured review verifying a service meets production standards (reliability, monitoring, emergency response) before/while SRE supports it — [Google SRE Book: Evolving SRE Engagement Model / PRR](https://sre.google/sre-book/evolving-sre-engagement-model/)
- GitLab publishes its production readiness review template publicly (operational risk assessment, monitoring, backup, security, performance sections) — usable as a PRR-lite crib — [GitLab Handbook: Production Readiness](https://handbook.gitlab.com/handbook/engineering/infrastructure/production/readiness)
- 2025 practitioner checklists (Cortex, Port, OpsLevel, DX) consistently include: observability (logs/metrics/traces + alert thresholds), documented runbooks/on-call ownership, tested backup and restore, security scanning, load/perf validation, and rollback/deployment safety — [Cortex: Production Readiness Checklist](https://www.cortex.io/post/how-to-create-a-great-production-readiness-checklist), [Port: Production readiness checklist](https://www.port.io/blog/production-readiness-checklist-ensuring-smooth-deployments), [OpsLevel: Production readiness in depth](https://www.opslevel.com/resources/production-readiness-in-depth), [getdx.com checklist](https://getdx.com/blog/production-readiness-checklist/)
- The "continuous PRR" argument (Jos Visser, ex-Google SRE): readiness is not a one-time gate but re-verified continuously as the service changes — [The Continuous Production Readiness Review](https://josvisser.substack.com/p/the-continuous-production-readiness)

### Inferences
- Duly PRR-lite (per release, enforceable as a PR-template checklist that agents must fill and the founder verifies): 1) alert exists for the failure mode this feature adds (deadline-computation errors, ingestion staleness); 2) runbook stub: how to re-run ingestion, how to correct a wrong deadline for a user; 3) `pg_restore` from last night's backup rehearsed monthly into a scratch DB (backup that is never restored is a documented anti-pattern across the cited checklists); 4) all webhook/notification/LLM-call jobs idempotent (idempotency keys) since the queue retries; 5) per-user and per-IP rate limits on API + LLM endpoints (also OWASP LLM10); 6) migration is reversible or has a documented forward-fix; 7) feature verified on the staging PaaS environment built from the same image.
- Compliance-specific addition for Duly beyond generic checklists: an immutable audit log of every deadline the system displayed to a user and the rule-version it was derived from — because "we told the user the wrong date" is the existential failure mode. No external source states this; it is a domain inference.

### Gaps
- No published "PRR-lite for solo founders" checklist found; the above is a scaled-down synthesis of Google/GitLab/vendor checklists.
