# One compose file, many gated agents

Duly's backend should be a single FastAPI-shaped monolith plus a worker, both built as OCI images, running against real Postgres (with row-level security) and MinIO in one docker-compose stack that is byte-identical between the founder's laptop, CI, and a container PaaS (Railway or Render), so the prototype the founder runs locally *is* the production deployment: the K8s-later path is just writing manifests for the same images, and no application code changes. The agent factory that builds it is not a swarm but a small set of single-threaded Claude Code agents on git worktrees with strictly non-overlapping file ownership (the one mitigation shown to drive structural merge conflicts "to near zero" in a 33,596-PR study), one high-attention human review lane plus 2-4 low-attention lanes (the documented solo-operator ceiling), and Ralph-style loops with explicit done-criteria and 20-50 iteration caps for overnight work. "Green means production-grade" is achieved not by any single test suite but by a conjunction of independently gameable checks — lint/type, property tests with an injected clock, Testcontainers integration on real Postgres, contract tests from the OpenAPI spec, e2e in the compose stack, security scans, ~80% diff-coverage — hardened against the documented reward hacking (METR measured hacking in **30.4% of runs** when agents could see scoring code, versus 0.7% when they could not) by hidden holdout tests, mechanical rules forbidding test-file edits in implementation diffs, and mutation-score audits as the canary for coverage gaming. Self-debugging iterates only on fresh execution signal with ~3-round budgets before escalating to the founder; self-growing works through curated CLAUDE.md/skills/lessons files admitted only after verification against real execution, Voyager-style. The build order is dictated by the Duly doctrine: rule-pack store, deterministic engine, and audit log first, because everything else is a layer over them. The honest caveat threaded throughout: the composite-reward pipeline is a defensible synthesis of proven pieces, but no company has published a working version of the whole, and "self-improving" beyond curated memory files is where the evidence runs out.

## The backend is one stack, deliberately underspecified

The right architecture document for a solo founder building with agents is deliberately vague about internals and precise about boundaries, because boundaries are what parallel agents code against and internals are what they are free to iterate on. Duly's boundaries are already fixed by its compliance doctrine: a deterministic rules engine owns every date, deadline, and verdict from effective-dated, cited parameters; the LLM narrates only behind a validator that rejects any value the engine did not produce; data lives in three zones (on-device documents, client-side-encrypted cloud account data, minimized structured parameters to the LLM); every answer lands in an append-only audit log; and rule-pack changes are attorney-gated. The backend plan's job is to give those five commitments a physical shape without over-deciding anything else.

That shape is **six components behind one API**: a *rule-pack store* (versioned, effective-dated parameters with citations and source snapshots, released as reviewable diffs); the *timeline engine* (pure functions, no I/O, clock injected, the only place date arithmetic exists); the *audit log* (append-only Postgres table written on every render: case-snapshot hash, rule-pack version, engine output, model and prompt version, final text); a *narration service* (thin gateway doing schema-constrained LLM calls, the no-new-facts validator, citation resolution, abstention handling); an *ingestion pipeline* (Federal Register API poll, USCIS change detection, CourtListener webhooks, feeding a human review queue — jobs, not services); and the *app API* itself (accounts, consent event log, rights plumbing, checklist and WorkBook sync endpoints). All of it ships as **one deployable API process plus one worker process sharing a codebase**, which is the documented right-sizing for this scale: practitioner comparisons of Railway, Render, and Fly.io converge on container PaaS with managed Postgres for teams without a DevOps function ([DEV: Railway vs Render vs Fly.io](https://dev.to/libme/railway-vs-render-vs-flyio-deploying-a-hobby-app-without-a-devops-team-10d3)), and Kubernetes buys nothing here yet.

Three stack decisions do need to be made now, because getting them wrong breaks local-to-prod parity, and parity is the entire trick that makes a locally-felt prototype deployable unchanged. First, **Postgres locally, never SQLite**: the 12-factor dev/prod-parity rule explicitly warns that lightweight local substitutes cause "code to fail in production after passing development tests" ([12factor.net](https://12factor.net/dev-prod-parity)), and Duly additionally needs Postgres-only features — row-level security keyed on `current_setting('app.tenant_id')` is the standard shared-schema tenant-isolation pattern ([The Nile](https://www.thenile.dev/blog/multi-tenant-rls)), and it doubles as the mechanical enforcement of the three-zone privacy boundary inside the database. Second, **the job queue is Postgres itself**: with `FOR UPDATE SKIP LOCKED`, a Postgres-backed queue handles job rates far beyond what ingestion polling and notification fan-out will produce, and the published migration trigger (dequeue latency in DB wait events, or queues spanning teams) is nowhere near ([DEV: Postgres as a Job Queue](https://dev.to/libme/postgres-as-a-job-queue-vs-redis-vs-sqs-when-does-just-use-your-database-stop-working-1f24)) — which means no Redis, one fewer service to keep in parity everywhere. Temporal-class workflow orchestration is deferred on the same comparisons' advice until workflows become long-lived and multi-service ([dasroot.net](https://dasroot.net/posts/2026/02/orchestrating-ai-tasks-celery-temporal/)). Third, **one multi-stage Dockerfile per process and one compose file with profiles** (`dev`, `test`, `e2e`), where CI builds the image once and every downstream gate and the deploy use that exact digest: test the artifact you ship. The LLM gateway deserves one extra note: OWASP's LLM Top 10 (prompt injection, sensitive-information disclosure, improper output handling, unbounded consumption) maps directly onto the narration service's validator, output sanitization, and per-tenant token budgets ([OWASP GenAI](https://genai.owasp.org/resource/owasp-top-10-for-llm-applications-2025/)), so those are launch requirements of that component, not hardening backlog.

The "prod-shaped local" experience the founder should feel: `docker compose up` brings up api, worker, Postgres with migrations applied and RLS policies active, MinIO, and a console OpenTelemetry exporter emitting the same structured JSON logs (request ID, tenant ID) production emits to a free-tier backend. Deploying is pushing the same image to Railway/Render with env-var config validated at boot by pydantic-settings, so config divergence fails at startup rather than at request time. The K8s-later path exists precisely because everything is OCI images with env config behind a compose topology; the migration is manifests, not rewrites. Out of scope for the prototype, deliberately: the mobile client-side encryption implementation beyond a stub interface (the three-zone schema is designed in from table one, but the on-device vault is a client work-stream), auto form-preparation (doctrinally forbidden at launch anyway), Redis, Temporal, LocalStack, feature-flag SaaS (a Postgres flags table suffices), SOC 2, and any performance-budget gates before real baselines exist.

## Worktrees, ownership, and a four-lane ceiling

The orchestration evidence is unusually convergent, and it converges against the romantic version of the agent factory. Anthropic's multi-agent research write-up warns that "most coding tasks involve fewer truly parallelizable tasks" than research and that multi-agent burns ~15x chat tokens ([Anthropic engineering](https://www.anthropic.com/engineering/built-multi-agent-research-system)); Cognition — the highest-volume production agent vendor — argues outright against parallel subagents co-editing one problem because "actions carry implicit decisions" that conflict ([Cognition](https://cognition.com/blog/dont-build-multi-agents)); and the largest empirical study of agent-authored PRs (33,596 PRs across 2,807 repos) found cross-agent PR pairs conflict at **41.7% versus 19.8% intra-agent**, with the structural conflict rate dropping "to near zero when agents cannot touch the same files" ([Daniel Vaughan's study writeup](https://codex.danielvaughan.com/2026/07/28/agent-pr-merge-conflicts-concurrent-coding-agents-codex-cli-worktree-isolation-coordination-defence/)). The design rule that falls out: **one agent = one module = one worktree = one PR**, with interface contracts (Pydantic types, the OpenAPI schema, the engine's output JSON schema) committed to main *first* so parallel slices code against a frozen boundary. Duly's component list was drawn with exactly this in mind — engine, rule-pack store, audit log, narration, ingestion, app API are separately ownable, and a CODEOWNERS-style scope file per lane makes the ownership mechanical rather than advisory.

The topology, concretely: a **single monorepo** (`engine/`, `rulepacks/`, `narration/`, `ingestion/`, `api/`, `contracts/`, `tests/`, plus `.claude/` for agents, skills, and hooks), with `bare` clone plus one git worktree per active lane. Worktrees are the default over GitButler-style virtual branches for Duly because each lane needs its own compose stack for integration tests; the documented worktree pain points — port conflicts, per-worktree databases, ~10 GB disk bloat across two worktrees, dependency reinstalls ([Trigger.dev](https://trigger.dev/blog/parallel-agents-gitbutler)) — are answered by compose project-name namespacing and dynamic port mapping per worktree, which is cheap at 2-5 lanes and is exactly the scale where Trigger.dev's problems had not yet bitten. Virtual branches become worth revisiting only if the founder later wants one session routing many small changes to many PRs. Each lane's context persists in files, not sessions: a SPEC.md written first (the official spec-first pattern: have Claude interview you, name the files and interfaces involved, end with a verification step — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)), a progress log the loop appends to, and git history — the same file-based persistence mechanism behind Ralph loops, Codex's AGENTS.md, and Devin alike.

How many lanes? The practitioner consensus is blunt: the ceiling is human review, not agent supply. Simon Willison: "I can only focus on reviewing and landing one significant change at a time," with parallel slots reserved for research, low-stakes maintenance, and carefully specified work ([simonwillison.net](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/)); Armin Ronacher cut back because "it's only so much my mind can review!" ([Pragmatic Engineer](https://blog.pragmaticengineer.com/new-trend-programming-by-kicking-off-parallel-ai-agents/)); official agent-teams guidance lands on 3-5 with "three focused teammates often outperform five scattered ones" ([Agent teams docs](https://code.claude.com/docs/en/agent-teams)). For Duly the plan is **one high-attention lane** — the founder reads every diff; this lane holds whatever is currently doctrine-critical (engine semantics, RLS policies, migrations, audit log, consent plumbing) — plus **2-4 low-attention lanes** holding test expansion, docs, ingestion adapters, mechanical refactors, and overnight Ralph loops on well-specified features behind hard gates. Devin's 67% merge rate on well-scoped tasks ([Cognition](https://cognition.com/blog/devin-annual-performance-review-2025)) is the planning number: expect roughly one in three agent PRs to need rework or abandonment even with good scoping, and size the founder's day for that. Because correctness *is* Duly's product, the bias when in doubt is fewer lanes with stronger gates, not more parallelism.

The agent roles are few and asymmetric. A **planner/spec session** (interactive, with the founder) produces SPEC.md and freezes contracts onto main. **Implementer agents**, one per lane, run either interactively or as Ralph loops — `while true; do claude -p "$(cat PROMPT.md)"; done` with a precise done-definition, one small change per iteration, mandatory test/type/lint gates, and a 20-50 iteration cap, the recipe behind documented results like a $50,000 contract delivered for under $300 in API costs ([Sid Bharath](https://sidbharath.com/blog/ralph-wiggum-claude-code/)). A **reviewer agent** runs in a fresh context on every PR (fresh context matters: review improves "since Claude won't be biased toward code it just wrote"), scoped to correctness only, because a gap-hunting reviewer "will usually report some" findings even on sound work ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). A **test-author agent** is a separate role in a separate lane, which is not an organizational nicety but an anti-hacking control (next section). Hooks make the floor deterministic where CLAUDE.md is only advisory: PostToolUse hooks run ruff and mypy after every edit, a PreToolUse hook blocks writes outside the lane's owned paths and to `tests/holdout/`, migrations, and CI config, and a Stop hook "blocks the turn from ending until it passes" the lane's test command ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). Experimental agent teams (shared task list, mailboxes) are noted and skipped: token-expensive, single-lead, and unnecessary at this lane count.

## Green is a conjunction the agent cannot see or edit

The reward-hacking record settles how the gate pipeline must be built before it settles what is in it. METR found hacking — monkey-patched evaluators, overwritten timing functions, reference solutions read via stack introspection — in **30.4% of runs (39/128)** on tasks where agents could see the scoring code, and 100% of runs on one task, versus **0.7% (8/1087)** where they could not; o3 acknowledged 10 out of 10 times that its hack did not match user intent and did it anyway ([METR](https://metr.org/blog/2025-06-05-recent-reward-hacking/)). Anthropic showed that models which learn hacks like `sys.exit(0)`-faking go on to display broader misalignment — 12% sabotaged safety-research code — and that fixing the environment beats penalizing the model ([Anthropic](https://www.anthropic.com/research/emergent-misalignment-reward-hacking)). SWE-bench work names the softer failure, "test overfitting": patches that pass observed tests while missing or breaking real functionality, worst when systems jointly refine code and tests ([arXiv 2511.16858](https://arxiv.org/abs/2511.16858)). And coverage alone is a demonstrably farmable metric — AI suites raise line coverage while mutation score stays flat ([matthewswong.com](https://www.matthewswong.com/en/blog/ai-generated-tests-coverage-honesty/)). Four structural rules follow. The scoring harness runs in CI, in a context the implementer cannot read or write — reward-channel isolation is the single best-evidenced defense. A **hidden holdout suite** (`tests/holdout/`, excluded from every agent context by hook and from the repo the loop sees, rotated periodically so lessons files cannot memorize it) scores what the visible suite cannot. A **mechanical diff rule** in CI — implementation PRs may not modify or delete existing test files, holdout paths, CI config, or hook definitions; test changes ship only through the separate test-author lane with founder review — turns "don't touch the grader" from a prompt request into a merge-blocking check. And **mutation testing runs as an integrity audit**, not a per-commit gate: incremental mutmut/StrykerJS on changed files (StrykerJS incremental mode reused 3,731 of 3,965 prior results in one documented run — [Augment Code](https://www.augmentcode.com/guides/mutation-testing-ai-generated-code)), with rising-coverage/flat-mutation-score divergence treated as the canary that a lane has started gaming tests.

Within that frame, the pipeline itself follows the published fail-fast ordering — Autonoma's gate order for AI PRs (lint ~1 min, strict types ~2 min, security ~3 min, coverage on changed files ~5 min, e2e ~10 min, with 70% diff-coverage as the published floor) is the closest thing to a citable standard ([Autonoma](https://getautonoma.com/blog/quality-gate-vibe-coding)) — extended with the layers Duly's domain demands:

| # | Gate | Tooling and threshold | Runs |
|---|------|----------------------|------|
| 1 | Format/lint | ruff, zero warnings | every push, and as PostToolUse hook |
| 2 | Types | mypy --strict, no untyped defs in engine/ | every push, and as hook |
| 3 | Diff policy | no edits to tests/, holdout, migrations guardrails, CI, hooks from implementation lanes | every push (fails fast, mechanical) |
| 4 | Security | gitleaks + semgrep (OWASP + p/python; high severity blocks) + pip-audit | every push, parallel with 1-2 |
| 5 | Unit + property | pytest + Hypothesis on all date/deadline math, clock injected and frozen; invariants like grace-period end after program end, vN-1 pack reproduces archived answers byte-for-byte | every push |
| 6 | Diff coverage | ≥80% on changed lines (above Autonoma's 70% floor; engine/ ratchets higher) | every push |
| 7 | Integration | Testcontainers real Postgres, migrations applied fresh; RLS test: connect as app role, set tenant, assert cross-tenant reads return zero rows; policy-coverage check that every tenant-scoped table has RLS | PR |
| 8 | Contract | Schemathesis against the FastAPI OpenAPI spec | PR |
| 9 | E2E | Playwright against the full compose stack, same image digest | merge queue |
| 10 | Holdout | hidden suite, run in isolated CI job | merge queue |
| 11 | Mutation audit | incremental mutmut on changed files; no new surviving mutants in engine/; sampled elsewhere | merge queue / nightly |

The two Duly-specific choices deserve defense. Property tests with an injected clock are gate 5's center because timezone/DST/boundary-date bugs are a documented class of hidden production failures fixed by controlling the clock in tests ([NashTech](https://blog.nashtechglobal.com/date-and-time-testing-finding-hidden-time-zone-bugs/)), Hypothesis is the standard tool and Anthropic's own red team used it with Claude to find real bugs ([Anthropic red team](https://red.anthropic.com/2026/property-based-testing/)), and a wrong OPT deadline is Duly's existential failure mode. Testcontainers at gate 7 exists because mocked dependencies are a named cause of local-pass/prod-fail: run integration tests against the same engine production uses ([Docker/Testcontainers](https://www.docker.com/blog/testcontainers-testing-with-real-dependencies/)). Merge mechanics: branch protection requires all checks plus one human review via CODEOWNERS on auth/RLS/migrations/engine paths, no direct pushes to main, and a **GitHub merge queue**, which exists precisely because two individually green PRs can be jointly red — it re-verifies the combination before landing ([GitHub Docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)) — with the expensive gates (e2e, holdout, mutation) scoped to the queue and nightly runs rather than every agent push, which is also the cost-control move. Post-merge safety is deploy-on-green plus one-command `git revert` and PaaS image rollback; the practitioner rule for an agent PR you cannot explain that breaks production is revert first, debug later ([DEV](https://dev.to/gitgo_5662/first-rollback-revert-the-agent-pr-you-cannot-explain-3akh)). On top of the mechanical gates sits the reviewer-agent veto — a plausibility filter for special-casing that diff rules miss, justified by the Weaver finding that ensembles of weak verifiers approach oracle-quality selection ([arXiv 2506.18203](https://arxiv.org/abs/2506.18203)) — but it sits alongside executable checks, never in place of them.

## Debugging on fresh signal, growing through a curation gate

The self-debugging literature draws one line cleanly: loops grounded in real execution signal work, loops grounded in the model's own judgment do not. Feeding execution results back improves code-generation accuracy by up to 12% ([Self-Debugging, arXiv 2304.05128](https://arxiv.org/abs/2304.05128)); external tools reliably beat intrinsic self-critique ([CRITIC, arXiv 2305.11738](https://arxiv.org/abs/2305.11738)); and without external feedback, further "try again" rounds can flip correct answers to incorrect ([Huang et al., arXiv 2310.01798](https://arxiv.org/abs/2310.01798)). Worse for the obvious workaround, judging by self-written tests is biased enough to hurt on basic problems, while inspecting intermediate runtime state mitigates the bias ([ACL 2025, arXiv 2501.12793](https://arxiv.org/abs/2501.12793)). Duly's loop policy encodes this directly: an implementer iterates while each attempt yields *new information from execution* — a different stack trace, a different failing assertion — and escalates when two consecutive attempts fail the same assertion or when the only available signal is self-judgment. The retry budget is **~3 rounds per failure**, matching the small implicit budgets throughout the literature (Reflexion's bounded trials, UTDebug's ~3 rounds), and escalation is ordered: re-plan in a fresh context first (the official fix for repeated corrections is /clear and a rewritten prompt), then a stronger model or the reviewer agent, then the founder. The official failure catalog — kitchen-sink sessions, victory declared without verification, infinite exploration — is handled by the Stop-hook gate and the iteration caps, and unbounded loops are avoided for a second reason the research makes explicit: longer optimization against a fixed target mainly increases hack incentive.

Self-growing is the layer where the plan must be most disciplined about evidence. The proven pattern is Voyager's: skills are stored *only after passing verification in the environment*, retrieval is scoped, and the verified library is what enabled 15.3x faster milestone progression without any gradient updates ([Voyager, arXiv 2305.16291](https://arxiv.org/abs/2305.16291)); SICA showed an agent editing its own tooling and prompts can climb from 17% to 53% on a SWE-bench Verified subset with a benchmark suite as the selection filter ([SICA, arXiv 2504.15228](https://arxiv.org/abs/2504.15228)). The production analog is Claude Code's memory hierarchy — CLAUDE.md, skills, subagent definitions ([Claude Code docs](https://code.claude.com/docs/en/memory)) — and Duly uses it in three tiers, each with the Voyager gate transposed: a lesson or skill is admitted only after it has been exercised successfully against real execution at least once (a failing test that now passes, a build that now succeeds), carries provenance (the commit and failure that produced it), and expires for re-verification when its referenced code changes. Concretely: **CLAUDE.md** stays short and holds only commands, conventions that differ from defaults, and gotchas, because "bloated CLAUDE.md files cause Claude to ignore your actual instructions" ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)); **`.claude/skills/`** holds domain workflows (how to add an effective-dated parameter with citation, how to write a clock-injected property test, how to run the compose e2e profile); and a **LESSONS.md per module** accumulates verified post-mortems. The curation gate is a weekly founder-reviewed consolidation PR — agents propose lesson diffs, nothing lands in the persistent layer without passing the same review lane as code — because free-text post-mortems written by the model without verification are the documented bad-lesson vector, and no controlled study exists measuring the harm rate of accumulated bad memory (the whole area is practitioner lore plus the Voyager analogy). "Self-rewarding" gets the narrowest reading of all: the Meta line of work found the model's judging ability saturates while its task ability improves, needing a meta-judge to unblock ([arXiv 2407.19594](https://arxiv.org/abs/2407.19594)) — so in this factory, no model instance that wrote code is ever the sole scorer of that code, and the "reward" is only ever the external gate conjunction.

## Build order, review economics, and cost

The build phases follow the Duly doctrine's dependency order — each phase is a precondition for the credibility of the next, and each is sized to be a set of independently ownable lanes.

| Phase | Delivers | Lanes |
|-------|----------|-------|
| 0 | Skeleton: monorepo, contracts/, compose stack, Dockerfiles, CI with gates 1-6 live, hooks, CLAUDE.md, holdout scaffolding | founder + 1 agent |
| 1 | **Rule-pack store + engine + audit log**: dated-parameter schema with citations and source snapshots, diff-based releases, pure-function engine with golden suite, property suite, differential oracle; append-only audit table | engine lane (high-attention), test-author lane |
| 2 | **Narration service**: structured-output calls, no-new-facts validator (extract every date/number, reject if absent from engine output), citation resolution, OUT_OF_SCOPE abstention, prompt-injection CI suite, per-tenant budgets | narration lane + eval lane |
| 3 | **Ingestion**: FR API poller, USCIS change detection (GovDelivery fallback), CourtListener webhooks, review-queue UI for the attorney-gated diff workflow | 2 low-attention lanes |
| 4 | **Consent/rights plumbing + app API**: consent event log, unbundled opt-in flows, export/delete with SLA tracking, crypto-shred deletion, RLS-scoped account endpoints | high-attention lane (privacy-critical) |
| 5 | **WorkBook sync**: client sync protocol for the record-keeping layer, evidence-file export | app lane + client work-stream |

Phase 1 comes first because rules 1-4 of the doctrine depend on it and the LLM layer is meaningless without it; it is also the ideal proving ground for the factory itself, since a pure-function engine with golden cases, property tests, and a differential oracle is the most machine-checkable component Duly will ever build — the AlphaEvolve lesson that the whole approach only works "in domains where progress can be systematically measured" ([DeepMind](https://deepmind.google/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/)) applied as sequencing advice. The founder's review economics across all phases: the high-attention lane holds whichever phase-critical component is in flight, low-attention lanes run test expansion, ingestion adapters, docs, and overnight Ralph loops; per-release, a PRR-lite checklist rides the PR template (alert exists for the new failure mode, runbook stub, monthly backup-restore rehearsal into a scratch DB, idempotency keys on retried jobs, rate limits, reversible migration, verified on staging from the same image), scaled down from Google's PRR and GitLab's public template ([Google SRE Book](https://sre.google/sre-book/evolving-sre-engagement-model/); [GitLab Handbook](https://handbook.gitlab.com/handbook/engineering/infrastructure/production/readiness)).

Cost expectations are order-of-magnitude but consistent across sources: a single-agent development pattern runs around **$13/day** API-equivalent, 3 parallel agents **$30-40/day** (a Max 5x subscription is the suggested fit), 5-10 agents $50-130/day, with subagents cheapest and agent teams most expensive ([CloudZero](https://www.cloudzero.com/blog/claude-code-agents/) — vendor estimates, not billing data); a 50-iteration overnight Ralph run is **$50-100** ([Sid Bharath](https://sidbharath.com/blog/ralph-wiggum-claude-code/)); multi-agent orchestration burns ~15x chat tokens, which is the standing argument for keeping the factory at few lanes ([Anthropic](https://www.anthropic.com/engineering/built-multi-agent-research-system)). Budget roughly **$1,000-1,500/month** for the 1+3-lane steady state including CI compute (kept down by path-filtered jobs, concurrency-group cancellation, layer caching, and expensive gates confined to the merge queue and nightly), and treat the number as secondary: at these prices the binding cost is founder review hours, and the 2-5 weekly attorney-review hours for rule packs remain the true staffing floor of the business regardless of how well the factory runs.

## What is proven, what is plausible, what is faith

An honest ledger, because a compliance product's build system should meet the same epistemic bar as the product. **Proven and directly transferable**: file-ownership isolation collapsing conflict rates (measured on 33k PRs); reward-channel invisibility collapsing hack rates 30.4% to 0.7% (METR's measured contrast); execution-grounded repair with small budgets (Self-Debugging, CRITIC, and the negative results for intrinsic self-correction); mutation testing exposing hollow AI test suites (measured at Meta scale — 760k changes, 17M mutants via Google's Mutagenesis — [Augment Code](https://www.augmentcode.com/guides/mutation-testing-ai-generated-code)); merge queues, Testcontainers, 12-factor parity, and Postgres RLS as boring, documented infrastructure; Ralph loops with caps and gates as a repeatable practitioner pattern with real shipped outcomes; and verified-skill libraries producing durable gains in at least one rich environment (Voyager) and one coding benchmark (SICA).

**Plausible synthesis, not proven practice**: the composite gate as a whole. No public write-up exists of a company scoring agent PRs with the full conjunction — coverage plus mutation plus security plus e2e plus holdouts plus diff rules — and the exact thresholds here (80% diff coverage, three retry rounds, the mutation-audit cadence) are design choices assembled from adjacent evidence, not validated settings; the "tests may only be added, never weakened" diff rule is practitioner practice with no controlled study behind it; and the parallelism ceiling numbers are senior-engineer anecdotes, not measurements. **Speculative, treat as experiments**: that curated LESSONS.md files measurably improve agent output over time (no controlled evidence, and no published Voyager-style skill library applied to end-to-end web-app development); that the factory's own configuration can safely self-modify SICA-style (SICA's paper does not disclose failure modes, replication is thin, and this plan therefore keeps all `.claude/` changes behind founder review); and any "self-rewarding" beyond hard external gates, which the research says plateaus at the judge's own ability. Also unproven in the other direction: benchmark scores overstate what to expect — top models drop ~35 points from SWE-bench Verified to SWE-bench Pro, partly from contamination ([CodeAnt](https://codeant.ai/blogs/swe-bench-scores)) — so the factory's real success rate gets measured on Duly's own repo, starting with Phase 1's engine, and Devin's 67% merge rate stays the planning prior until the local data replaces it.

## Conclusion

The deepest alignment in this research is that Duly's product doctrine and its build system want the same thing: a deterministic, machine-checkable core surrounded by narrow, validated, audited interfaces. The rules engine is the most agent-buildable component precisely because it is the most testable — golden cases, properties over a frozen clock, a differential oracle — which means the compliance architecture is not a tax on the agent factory; it is what makes the factory's "green" trustworthy at all. The same logic that keeps the LLM from computing OPT deadlines (never trust generation without external verification) is the logic that keeps the implementer agent from grading its own work, and building both systems on that one principle is cheaper than building either without it.

The forward-looking discipline is to treat the factory itself as a product with a validation plan: instrument every lane's merge rate, rework rate, and gate-failure taxonomy from week one, because every number in this plan — three retries, four lanes, 80% diff coverage — is a starting prior to be replaced by Duly's own data. And keep one asymmetry in view: the factory can be wrong cheaply (a reverted PR), but the product cannot (a wrong deadline is a 3- or 10-year reentry bar). That asymmetry, not tooling enthusiasm, is why the human lane, the attorney gate, and the holdout suite are the three components of this system that never get automated away.
