## Findings

### 1. Blocking: on the packaged desktop engine, POST /v1/schedule answers 500 to every request

- Breaks: SPEC-W2 point 47 ("A1 POST /v1/schedule ... served by api/desktop_main.py") and
  point 22 (the Loop gets its dates from engine.schedule).
- Where: api/case.py:63, `_schedule_validator` reads `REPO_ROOT / "contracts" /
  "schedule.schema.json"` on the first request.
- The cause: desktop/python/bundle.json does not list that file. tests/unit/desktop_entry/
  test_bundle_inputs.py also pins the bundle's contracts to exactly four files ("and no others").
- Input: a valid body `{"case": <the tests' CASE>, "requests": [{"id": "a", "from": {"today":
  true}, "add": {"days": 1}, "sign": 1}]}` with the launch token, sent to create_app from the
  allowlist-only tree.
- What happens: 500, `FileNotFoundError: .../contracts/schedule.schema.json`. The same script on
  the repository tree gives 200 with 2026-10-04.
- So the route differs between the server and the desktop, which is what this review was asked
  to look for hardest.
- Why the tests miss it: test_local_routes_w2.py builds the desktop app in the repository tree,
  where the file exists.
- What fixing it needs: the founder must either let the bundle hold schedule.schema.json (a
  change to SPEC-W1 point 14 and its test, which no lane may edit), or the request must be
  checked without reading that file at run time.

### 2. Should fix: an update that update.schema.json refuses is still served

- Where: api/case.py:76, `published_updates`. It serves every published file that
  publish_blockers passes. publish_blockers (pipeline/graph.py:34) tests truthiness, so the
  strings "false" and "no" pass it.
- Input: a file in the published folder with `approval: {"approved": "false", "approved_by":
  "x"}`, every `quote_found: "false"`, and checks `"no"`.
- What happens: GET /v1/updates returns it. update.schema.json gives "'false' is not of type
  'boolean'". An approved copy without `approved_at` is also served, which is a schema error too.
- The rule it falls short of: openapi /v1/updates says "Each follows
  contracts/update.schema.json".
- Fix: validate each published file against update.schema.json before publish_blockers.

### 3. Should fix: no test fails when the publish_blockers filter is removed

- Where: tests/unit/api/test_local_routes_w2.py:204.
- Mutant M3: `return updates` in place of the filter.
- What happens: every test passes. pipeline/published/ does not exist, so each test compares an
  empty list with an empty list.
- Fix: a test that points PUBLISHED at a temporary folder holding one refused file and one
  passing file.

### 4. Should fix: no test pins the cap's boundary day

- Where: tests/unit/engine/test_schedule.py:493.
- Mutant M2: `found > cap_date + timedelta(days=1)`.
- Input: from 2026-04-30, + 2 days, cap opt.file_by.closes.a1.
- What happens: the mutant dates it 2026-05-02, one day past the obligation, without capped. The
  60-example property test passed on it.
- The property is named in SPEC-W2 point 51. It needs a fixed example where the uncapped result
  is exactly the cap plus one day.

### 5. Should fix: Juneteenth before 2021-06-17, and days with no holiday row, are untested

- Where: tests/unit/engine/test_schedule.py:304. The bases run from 2022 to 2034.
- Mutant M1 counts 2020-06-19 as a holiday. Mutant M7 counts a day with no row in force as a
  business day (a guess). Both survive.
- Input for M7: 1985-12-30 + 3 business days. Correct code gives 422; the mutant gives a date.

### 6. Should fix: a body inside the contract crashes the route

- Where: engine/schedule.py:100 to 104.
- Inputs: `{"days": 1000000000}` from today; `{"months": 1000000}`; or `{"date": "0001-01-01"}`
  with `{"days": 1}` and sign -1.
- What happens: each gives 500 (OverflowError), where openapi declares 422 for a body it cannot
  take.
- A related stall: `{"business_days": 100000}` takes 0.5 s. The contract allows 1000 requests
  with no maximum, so one body of 1000 requests near 2,000,000 business days would take hours.
- Fix: a `maximum` in the contract (founder), or a 422 when the result falls outside
  date.min..date.max.

### 7. Should fix: the desktop cannot serve a published update

- Breaks the letter of SPEC-W2 point 47: "W1's allowlist gains pipeline/published/*.json".
- Where: desktop/python/bundle.json. pipeline/ is forbidden by test_bundle_inputs.py. Also,
  api/case.py:85 imports pipeline.graph, which imports langgraph, and langgraph is forbidden in
  the desktop group (SPEC-W1 point 13).
- Today the result is an empty list on both apps. Once a file is published, the server will
  serve it and the desktop will not.
- If the JSON alone is bundled, the import fails with ModuleNotFoundError.
- plan-w2-p3 told L-api to report this for the founder. api/PROGRESS.md does not record that it
  did, so I list it under requests.

### 8. Should fix: a date counted from a planning item is not marked planning

- Where: engine/schedule.py:75.
- Input: `{"from": {"item": "opt.prepare.opens.a1"}, "add": {"days": 0}, "sign": 1}`. That item
  carries `planning: true` (it is set by plan.prepare_months).
- What happens: the answer is 2026-01-14 with no planning flag, and rule_ids is
  [opt.apply_before_days] only.
- The contract says planning is "present only when the amount came from a product setting", so
  the code follows the contract. But SPEC-W2 point 41 says "only when a setting set it", and this
  date was set by one. This is a gap for the founder.

### Notes

- api/local_routes.py:30: the route's NAMES pattern takes `_` and `.` in categories, where
  openapi says `^[a-z0-9]+$`. The `fields` query is not read at all (it never matches, as the
  docstring says).
- Ids are not checked for being unique. The contract says "Unique within one request"; two
  requests with id `dup` both get answers.
- One business-day request that crosses a day with no holiday row turns the whole body into a
  422, so the other requests in it get no answers. L-engine says the contract has no reason for
  this case.
- An answer whose base item is litigated (for example opt.last_day.closes.a1) carries only the
  rule ids, not the status. A caller has to look the status up.
- SPEC-W2 point 51 still says the articles go to pipeline/published/. The plan moved them to
  drafts because no lane can record approval, and they correctly sit in drafts with approval
  false.
- The drafts are information only. No line is addressed to the student or says what anyone
  should do. Their quotes are found in the saved copies. One claim cites a CourtListener search
  listing of docket entries as primary. The entries are court records, but they were read
  through a third party.
- Overbuilding: none found. `_json`, `_checked_case` and `_names` each have two uses. The move of
  JUNETEENTH_ITEM and first_schema_problem reuse what was there.
