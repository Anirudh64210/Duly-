## Findings

### 1. Should fix: the route still turns a missing holiday row into a 422, but that code can no longer run

- Where: api/local_routes.py:34 (NO_CALENDAR) and api/local_routes.py:130 to 131.
- engine/schedule.py:120 now catches CalendarNotInForceError inside each request, and is_holiday
  is only called from there. So the route's handler never runs.
- Input: 1985-12-30 + 3 business days. The answer is 200 with holidays_not_known, and mutant M17
  (the handler removed) passes every test.
- Why it matters: openapi now says "A request the engine cannot date is not a 422", and the
  handler and NO_CALENDAR's words say the opposite to the next reader. Delete both and the
  import of CalendarNotInForceError in local_routes.py.

### 2. Should fix: one malformed file in pipeline/published/ makes GET /v1/updates a 500 on both apps

- Where: api/case.py:87, `json.loads(p.read_text())` for every file, before the schema check.
- Input: pipeline/published/ holding one valid, unblocked update and one file containing
  `{not json`.
- What happens: 500 Internal Server Error, so the valid update is not served either. A file
  holding `[]` is skipped correctly (the schema check refuses it).
- Only the founder's approval writes that folder, so this is not reachable by a user. But the
  route's rule is "a file outside update.schema.json is never returned", and a file that is not
  JSON at all is the plainest such file. Fix: treat a file that does not parse as one that does
  not follow the schema, with a test beside test_review_w2p3_2_3.

### Notes

- A date counted from a planning base and then capped to a rule item (not planning) is still
  marked planning, since the base was planning. That follows the contract's words as of a3f7a7a
  ("the amount ..., or the base item, or the cap item when the answer is capped"). The date shown
  is then the obligation's own day, so the founder may want the cap to decide in that case. No
  item in the F-1 pack today has a planning base before a rule cap in the Loop.
- An answer whose base item is litigated still carries only rule_ids, not the status (as in the
  first review).
- `amount > (last - first).days` in engine/schedule.py:111 is not reachable through the route,
  since the contract's maxima are below the readable span (54,785 days). It still guards a
  product setting larger than that span. It is three lines and is the overflow guard the plan
  asked for, so I do not count it as overbuilding.
- The drafts in pipeline/drafts/ are unchanged since the first review, and they stay there

- Overbuilding: only finding 1. engine/updates.py is a move, not a copy: pipeline/graph.py now
