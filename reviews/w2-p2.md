## Findings

### 1. Blocking: a trip with no return reads its absence window as done, so it leaves upcoming
engine/path.py:1469-1483 (`_window`, the "point 55" block added by fix3, ac6a06a).
Input: program p1 in progress to 2027-05-15, home address, `trip(left_on="2026-09-20")` with no
`returned_on`, today 2026-10-02 ($TMPDIR/rvp3/d3.py).
What happens: `trip.absence_limit.t1` shows 2026-09-20 to 2027-02-20 with no `waits_on`, and
`trip.absence_limit.closes.t1` is not in `upcoming`. The window is read as done. With the block
taken out (mutant M12), the same input gives the closing day in `upcoming` with waits_on
`t1.returned_on`, as before fix3. The block treats a `done_when` field left empty and asked as
"known whatever the answer". It is not: under point 2 the fill domain of an `ask` field
includes NONE, and point 30 says "All N: not done. Otherwise the window keeps its dates ..., stays
in upcoming and open items, and carries `waits_on` naming the gap." For a person abroad today, the
one date that matters most, the day five months after leaving, drops out of upcoming with nothing
said, on a guess that they are back. D92 (point 61): a trip with no return date is asked, not
assumed. The return is still asked, but the window behaves as if it had been answered.
test_review4b pins this behaviour: it requires the window's `waits_on` with the return left out
to equal its `waits_on` with the return entered. That contradicts point 30, so I list it under
disputes. A narrower fix that keeps fix3's aim: leave `done` as point 30 says and rely on `over`
(point 8) where the closing day is known and past.
spec_point: SPEC-W2-UNKNOWN point 30; D92 (point 61).
