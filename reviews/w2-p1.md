## Findings

### 1. Blocking: a STEM card with no employer drops both new-employer report windows, and nothing asks
`rulepacks/f1-us/v2026.09/parameters.yaml:2059` with `engine/path.py:610`.
Input: the case from test_a_new_employer_during_stem_gives_the_new_plan_window, with `employer`
removed from a2 (the STEM card). w1 is with e1 from 2026-07-01 to 2026-08-02, w2 is with e2 from
2026-08-03, and today is 2026-09-29. What happens: there is no stem_job_start stage, no
new_plan window and no report window. No question asks for a2.employer, and no reason in the
verdict names it. With employer e1 on a2, the same case gives both windows, 2026-08-03 to
2026-08-13. The where condition `this.employer differs_from this.under.employer` is unknown, so
`_select` returns None. `run_stages` then reads it as `or []` and drops the trace without
`_need`. A gap in the person's record removes a 10-day deadline from the regulation without a
question (SPEC-W2 45 P3, (f)(10)(ii)(C)(7)(iv), PRINCIPLES 2). The fix is generic: when a
for_each selection is unknown, ask for what it read. Alternatively, the pack can ask for the
card's employer. No test covers it.

### 2. Should fix: a planning date's working leaves out the setting
`engine/path.py:276`. Input: web/samples/path-stem-next.json, item opt.prepare.opens.a2. Its
inputs are {p1.end_date: 2025-12-13} and its rule_ids are [opt.apply_before_days]. Those two give
2025-09-14, but the value is 2025-08-14. The Timeline's "How Duly counted" shows only that input
and that rule, so the month comes from nowhere the person can see (BOUNDARY A3, "show the
working"). Put the setting and its value in the item's inputs. The label's "a planning date"
is the only mark a reader gets.

### 3. Should fix: no limit day for a card that has not started yet
`engine/path.py:1194`. Input: an OPT card from 2026-10-15 to 2027-10-14, no job, today
2026-09-29. If nothing changes, the count reaches 90 on 2027-01-12. The engine gives null,
because `_days_without` returns [] whenever today is before the start. Null also means "never
reached" and "not known", so a reader cannot tell the three apart (point 46 N2).

### 4. Should fix: no test checks the STEM report window or the "during the extension" filter
`tests/unit/engine/test_w2_windows.py`. Mutant M7 drops `this.start on_or_after
this.under.card_start` (parameters.yaml:2058). It passes every W2 test and the holdout, and then
a job with a new employer that began before the STEM card gets a new I-983 window. Mutant M5
dates stem_job_start.report from stem.new_plan_due_days and also passes, because no test reads
the report window or stem.report_change_within_days.

### 5. Should fix: an unknown setting id loads, then fails every compute
`engine/rulepack.py:130`. Input: a toy pack with a window opening at `{setting:
no.such.setting, sign: -1}`. validate_pack accepts it, and compute raises `SettingsError`. A
setting with a unit the engine cannot add (loop.weekly_budget, "check-ins per week") loads and
gives opens null, with no reason. The loader that already refuses a misplaced setting could also
refuse an unknown id and a non-date unit.

### 6. Should fix: the job-start report is a reading but is shown as verbatim
parameters.yaml:2040. The CHANGELOG says "Reading: a new job is a change in employment
information". Yet opt_job_start.report items carry reading: false, because the row behind them
is verbatim. PRINCIPLES 1 asks for a reading to be marked everywhere it is shown. Either mark
the window as a reading or record the reading on a rule.

### 7. Should fix: the CHANGELOG contradicts the founder fix
`rulepacks/f1-us/v2026.09/CHANGELOG.md:250` still says that the recommendation member is
"skipped while dso_on is not entered". After c24c65d it is required, and missing means Can't
tell yet.

### 8. Should fix (overbuilt): the setting is looked up twice
`engine/path.py:282` scans `settings["settings"]` again for the unit, right after
`whole_setting` scanned it for the value. engine/settings.py could return the value and the unit
together.
