## Findings

1. **should_fix (spec_gap; SPEC-W2 point 16 as D96 amends it).** The code follows the contract as
   of 444fa86, but SPEC-W2 point 16 and D96 still say the opposite. docstore.ts:250-252 and
   270-274.
   - Input: keys.bin present, no documents.bin, and files/ empty or missing (K1).
   - What happens: list answers ok with no documents, and a new documents.bin is written. That is
     what the contract now says: "keys.bin with no file in files/ is not index_missing: no
     document can be lost, so a new empty index is written".
   - SPEC-W2 point 16 still says: "a missing documents.bin while keys.bin or a file in files/
     remains is refused as index_missing, and nothing is read, written or deleted". D96 says the
     same ("while keys or files remain").
   - The plan's goal and the contract lane chose the new rule, and the rule is sound: with no
     encrypted file, no document can be lost. Only history lines can be, and they could not be
     read without documents.bin anyway.
   - The SPEC point and the decision need the founder's amendment so the three sources agree. I
     list it under disputes and requests in REPORT.json. No implementation lane can edit
     DECISIONS.md, and I do not hold the SPEC.
2. **should_fix (missing_test; contract store_full and bad_replaces, D96).** Four paths survive
   every test (mutants in $TMPDIR/mt9/mut.py; each changes behaviour on the input named):
   - **F3**, docstore.ts:386 (`hashes.add(checked.hash)` removed). Input: 4999 held, then
     add([b.pdf, b2.pdf]) where b2.pdf has the same bytes as b.pdf. On HEAD it adds one (S1b).
     Under the mutant it is store_full. The contract says "Files skipped (a duplicate ...) do not
     count", and a duplicate inside the same add is one of those.
   - **N6d**, docbridge.ts:207 (`count > 1` read as `paths.length > 1`). Input: a drop of
     ["notes.pdf" (not a whole path), "/Users/s/i20.pdf"] with replaces old. On HEAD this is
     bad_replaces (probe d.test.ts printed it), since the contract says "the add holds more than one file". Under the mutant,
     i20.pdf is added as a version of old. Now that the bridge is the only place this rule lives,
     this edge is its whole reason for counting skipped drops.
   - **R4**, reminders.ts:23-24 (keyed by id only). Input: loop.a shown on 2026-10-06, then moved to
     2026-10-09. On HEAD it shows again on 10-09 (N5: "moved date shows again: 3"). Under the
     mutant it never does. The file's own comment promises this, and no test checks it.
   - **R5**, reminders.ts:55 (the plan filter removed in keep). Under the mutant the record keeps
     the keys of reminders no longer planned and grows without end. No test reads its size.
3. **note (overbuilt).** docstore.ts:378-391. The store_full pre-count calls `check`, which reads
   every file in full, and then the add loop reads each file again.
   - It runs only when rows + paths > 5000, so at most 50 files of up to 50 MiB are read twice,
     near the cap only.
   - It is right, and `check` serves both loops, so I do not ask for a change.
   - Because of the double read, a file that changes between the two reads is counted by its
     first bytes. A store could then reach 5001 only if a file goes from duplicate to new during
     the add. I could not name a real student action that does this.
4. **note.** A build at 8637df1 (fix0) wrote `<userData>/reminders-shown.json` with the plain
   hashes. Nothing at HEAD reads or removes that file, so on a Mac that ran that build it stays
   after Delete everything. That build was never released, as far as the repository shows, so
   this is a note.
5. **note.** docstore.ts:233-234. `stored()` counts any name in files/ that is not .part,
   including a sub-folder (K5) or a .DS_Store. With keys.bin and no documents.bin, that means
   index_missing and not an empty index. This is the cautious side, and the contract says "a
   file", so I ask for no change. A comment would help the next reader.

## What holds

- **A missing index.**
  - It never deletes. Only .part files are swept.
  - index_missing now needs a file that would lose its name (K2, K3).
  - The store writes the empty index in the same step that makes keys.bin. If that write fails,
    the add is cannot_store, and the next launch starts clean (K6, N2).
- **Version chains.** These are all bad_replaces, and the 200 cap holds through add and through
  update (N4b and N4c caught):
  - a second replacer
  - a multi-file add that replaces
  - a 201st version
- **Limits.** 50 per add, 5000 documents, 20000 history lines and 200 versions each match a
  maxItems in the contract. store_full now counts only what would be stored, and the edge is
  tested at 4999 and 5000 (F1, F2 and F4 caught).
- **Reminders.**
  - The record is encrypted with safeStorage as state.bin is (R1 caught).
  - Delete everything removes it on both halves (R2 and R3 caught).
  - One reminder gives one Notification across a relaunch.
  - A damaged record, or another keychain's record, means "none shown yet". It never crashes.
- **Boundary and copy.** No new words reach a person. Refusals are codes, Notifications carry
  only the saved title and body, and the copy lint is clean. No date is computed here: main
  compares the date it is given with the saved one.
- **Chunks and engine.** All mutants on the chunk format (M1, M2, M3, M6, M17) and the reply check
  (M13) are caught.
